# 事务、幂等与并发设计

## 库存模型

每个商品在 `inventory` 表中有三类计数：

- `on_hand_quantity`：实际持有的实物库存。
- `regular_reserved_quantity`：普通销售订单仍占用的实物库存。
- `presale_reserved_quantity`：仍有效的预售订单占用的预售名额。

普通销售可售量为 `on_hand_quantity - regular_reserved_quantity`。预售容量保存在商品的 `presale_limit` 中，预售可用名额为 `presale_limit - presale_reserved_quantity`。预售名额不增加或扣减实物库存。取消订单时释放其原销售类型对应的预留计数。

数据库检查约束保证实物库存和各预留计数非负、普通预留不超过实物库存；应用在锁住商品及库存行后检查预售上限。

## 创建订单事务

`OrderService.create` 的整个公开入口带有 `@Transactional`。一个订单的订单行、普通/预售预留计数、幂等键和库存流水在同一 PostgreSQL 事务内提交。业务校验失败、库存不足、唯一约束失败或运行时异常都会回滚已写入的订单行和流水。

在检查和修改库存之前，服务按商品编号排序，并逐个执行 `SELECT ... FOR UPDATE` 锁定商品和库存行。相同商品的并发请求会在数据库行锁处排队，后一个事务读取前一个事务提交后的计数，再检查可售数量。因此库存正确性由数据库共享锁保证，不依赖 JVM 内的 `synchronized`，多个服务实例也竞争同一批数据库行锁。调整库存、修改预售规则和取消预留也锁定同一商品行。

多商品订单使用固定顺序获取库存锁，避免两个订单以相反商品顺序持锁。订单取消先锁订单行，再按相同商品顺序锁库存；同一订单同时取消时，后一个请求等待订单行锁并在看到 `CANCELLED` 后直接返回，不重复释放库存。

## 幂等处理

订单表对 `idempotency_key` 建唯一约束。创建请求在事务开始时插入订单和 key：

1. 首个请求取得 key 后按排序后的商品编号和数量生成 SHA-256 请求摘要。
2. 同 key、同摘要的重复请求读取并返回已保存订单，HTTP 状态为 `200`。
3. 同 key、不同摘要的请求返回 `409 Conflict`。
4. 不足库存等失败请求使整个事务回滚，因此失败 key 不会被占用；修复库存后可重试同一 key。

数据库唯一索引会协调同时到达的相同 key 请求。请求内容与订单创建、库存预留及流水写入保持原子性，所以重复请求不会再次占用库存。

## 库存流水

`inventory_movements` 只追加记录，不更新旧流水。记录包含实物库存变更、普通预留变更、预售预留变更、变更后计数、原因和可选的订单编号。商品初始库存、人工库存调整、订单预留和取消释放均有对应记录。

## 自动化验证

`InventoryWorkflowTest` 使用 Testcontainers 启动真实 PostgreSQL，验证重复提交、不同 payload 复用 key、多个同时到达的同 key 请求只创建一个订单、多商品失败回滚、预售上限与取消释放，以及多个并发订单竞争有限普通库存。无 Docker 的机器会跳过此集成测试类，普通单元测试仍运行；CI runner 提供 Docker 后执行全部测试。

该服务没有支付或订单完成流程，因此成功创建的 `RESERVED` 订单会持续占用名额，直至调用取消接口。此示例没有设置过期任务或幂等 key 清理策略。
